AI LeetCode Coach — Build Prompts (Updated Flow)
====================================================

This file splits the project into small, sequential parts. Each part is a
self-contained prompt you can hand to a developer or an AI coding assistant.
Run them in order — each later part builds on the files created earlier.

The code is organised as:

    client/   React (Vite) + Tailwind   — the whole UI lives here (local mode)
    server/   Express 5                 — fetches LeetCode data (GraphQL + REST)
    client/src/data/leetcode-problems.json   — the "important questions" list


THE UPDATED FLOW (what we are building)
---------------------------------------

  1. User enters a LeetCode profile URL.
  2. Backend extracts the username and fetches the solved questions.
  3. User selects HOW MANY questions they want to solve (total).
  4. The system compares solved questions vs the important list,
     splitting them into "already solved" and "not solved".
  5. The system suggests a MIX: some unsolved (new practice) + some solved
     (revision), such that the total equals the number picked.
  6. Output: the selected set (mix of solved + unsolved) is shown.
  7. A Sync button re-fetches solved questions, updates the data, and
     recalculates the suggestions.

The solved/unsolved split is decided AUTOMATICALLY by the system (the user only
picks the total). Default mix is ~40% solved (revision) and ~60% unsolved
(new), clamped to whatever the user has actually solved / still has left.


HOW TO USE THIS FILE
--------------------

- One prompt = one unit of work. The app should still run at the end of each.
- Run in order. Match the repo conventions: ES modules, camelCase modules,
  PascalCase components, services own logic, controllers only serialize.
- Keep every external call (LeetCode) bounded and fail gracefully.

PART 2 — Important questions data
----------------------------------------------------------------

Purpose: the fixed "important list" the system compares solved problems against.

Files (create):
  client/src/data/leetcode-problems.json

Prompt:
  Create `client/src/data/leetcode-problems.json` containing the important
  questions list as a JSON array. Each item has: `id` (number), `titleSlug`
  (unique, kebab-case, e.g. "two-sum"), `title` ("Two Sum"), `difficulty`
  ("Easy" | "Medium" | "Hard"), `tags` (array of topic strings), `paidOnly`
  (boolean), and `url` (https://leetcode.com/problems/<slug>/). Include a
  breadth of classic interview problems across the main topics (Arrays, Strings,
  Linked List, Trees, Graph, DP, etc.). Make sure the file is valid JSON
  (one item per line, no duplicate keys) — the app will `import` it directly.

PART 3 — LeetCode fetch (backend)
----------------------------------------------------------------

Purpose: fetch a profile + the full list of solved slugs from LeetCode.

Files (create):
  server/services/leetcode/client.js
  server/services/leetcode/queries.js
  server/services/leetcode/normalizer.js

Prompt:
  Implement the LeetCode integration layer. In `client.js`, route all requests
  through the system `curl` binary (LeetCode blocks non-browser TLS, so Node's
  native fetch fails): add a helper that spawns `curl`, captures stdout/stderr,
  appends `-w __HTTP_STATUS__:%{http_code}`, and parses out the status. Cache a
  `csrftoken` cookie (fetch the homepage once, read `csrftoken` from the cookie
  jar, retry once on a 403). Export `leetcodeRequest(query, variables, username)`
  that POSTs a GraphQL operation to `https://leetcode.com/graphql` with the CSRF
  token + browser-like headers, and a best-effort `fetchAcSubmissionSlugs(username)`
  that GETs `https://leetcode.com/api/<username>/acSubmission/` and reduces the
  accepted submissions to a unique `titleSlug` array (return `[]` on any error).
  In `queries.js` add three GraphQL operations: user public profile (submitStats
  acSubmissionNum by difficulty, profile fields, badges, userCalendar), contest
  ranking, and recent submissions. In `normalizer.js` write `normalizeProfile`
  (per-difficulty solved counts, acceptance rate, badges, calendar/streak,
  heatmap, recent submissions) and a `uniqueSlugs` dedupe helper.

PART 6 — Compare logic (solved vs important list)
----------------------------------------------------------------

Purpose: turn the profile into an analysis that partitions the important list.

Files (modify):
  client/src/lib/leetcode.js  — add `buildAnalysis`

Prompt:
  Add `buildAnalysis(profile)` to `client/src/lib/leetcode.js`. Build a
  `solvedSet = new Set(profile.solvedSlugs || [])`. Pull total / easy / medium /
  hard solved counts and acceptance rate / streak / rating from the profile.
  Compute per-topic coverage across the important list: for every problem, for
  every tag, count total and solved, producing `topics` sorted by lowest
  coverage first. Derive `weakTopics` (lowest coverage, capped ~6) and
  `strongTopics`. Compute `datasetSolved` (important-list problems in the
  solvedSet) and `datasetUnsolved`. Add a small rule-based `insights[]` (hard
  share, easy-vs-medium balance, acceptance rate, streak, contest rating, weakest
  topics). Return an object containing all of the above plus `solvedSet`.

PART 7 — Suggestion logic (the auto mix)
----------------------------------------------------------------

Purpose: the core change — user picks a total, system derives the mix.

Files (modify):
  client/src/lib/leetcode.js  — add `deriveSolvedCount` + `buildPlan`

Prompt:
  Add two functions to `client/src/lib/leetcode.js`. First a module-level
  `FREE_PROBLEMS = PROBLEMS.filter((p) => !p.paidOnly)` constant (paid-only
  problems are never offered as new practice). Then `deriveSolvedCount(analysis,
  total)`: start with `Math.round(total * 0.4)` solved, clamp down to how many
  the user has actually solved in the important set (`analysis.datasetSolved`),
  clamp up so we never ask for more fresh problems than are left
  (`total - FREE_PROBLEMS.filter(p => !solvedSet.has(p.titleSlug)).length`),
  and finally clamp into `[0, total]`. Then `buildPlan(analysis, total)` that
  calls `deriveSolvedCount`, ranks problems by weak-topic membership first then
  difficulty (revision = solved pool sorted hardest-first-in-weakness; fresh =
  `FREE_PROBLEMS` unsolved pool sorted easiest-first), slices `solvedCount`
  revision and `total - solvedCount` fresh, and returns
  `{ revision, fresh, solvedCount }`. Remove any notion of the user supplying
  the solved split — it must be computed here.

NOTES / CONVENTIONS
-------------------

- The important list lives in `client/src/data/leetcode-problems.json`; the
  "important questions" in the flow refer to this file.
- The mix is automatic — there is no user-facing "solved count" input anywhere.
- `paidOnly` problems are excluded from "new practice" but may appear in
  "revision" if the user has actually solved them.
- LeetCode calls are best-effort: if the solved-slugs endpoint fails, the fetch
  still succeeds with an empty `solvedSlugs` (recommendations become less
  personalized rather than failing).
- State is device-local (localStorage); there is no server-side database in
  this reduced build. "Update the database" in the flow means re-fetching and
  re-storing the latest solved list.
